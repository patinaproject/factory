### Triage

**You own the verdict. Investigate, decide, record.** The run is unattended whoever starts it. No step waits for a reply. Adapted from Lauren Tan's Benny `triage-issue-reports`.

Reach the tracker only through the repository's issue-tracker adapter, and only from the coordinator. Subagents are read-only and return findings. Every subagent prompt forbids tracker writes. When the adapter lacks an operation a step needs, skip that write and name the gap in the reply. Never improvise a tracker write.

1. **Freeze.** Record the issue identifier and repository once. Every later read and write uses them.
2. **Check idempotency and ownership.** Read the issue's state, labels, triage notes, and linked pull requests. Stop when the notes already hold a verdict that no later comment or edit outdates, when a person is assigned and working on it, or when an open pull request already addresses it. A stop writes nothing but step 13's priority and its Decision log entry.
3. **Read the whole report.** Read the body, every comment, and every attachment at full resolution. Capture expected and observed behavior, environment, trigger, frequency, error text, and linked issues, commits, or pull requests. Name an attachment you cannot read as unread. Never describe it. Use evidence already in the issue before asking for more.
4. **Classify.** Decide one Type from the repository's Type set and at most one Theme, both from the adapter's **Labels** section. The Type's row there says how to verify the claim. Then sort the issue as trivial, such as a typo or a one-line change with an obvious location, or standard. Trivial issues skip steps 10 and 11 and the parallel reproduction in step 6.
5. **Trace the cause.** Run **how** over the path from the reported action to the observed result, and check whether the symptom belongs to that path or to a dependency. On standard issues, run two **why** investigators: one for regressions and earlier attempts, one for existing fixes, open work, and earlier rejections. Keep confirmed facts and hypotheses in separate lists. When the Type calls for a redundancy check, search the codebase for an existing implementation and record where you looked. When it calls for confirming a one-off action, confirm the action has not already been done. When it calls for checking existing designs, search the design files and earlier design issues for the same flow or screen.
6. **Reproduce (when the Type calls for reproduction).** Give one subagent on the bug-fix role the trace and the report. It returns the command and output, or what it tried. Re-run a claimed reproduction yourself before you count it. When it fails and the code path is still unclear, run up to three parallel attempts with different strategies through **swarm**. Then take one of three results:
   - **Reproduced.** Record the command and output.
   - **Diagnosed, not reproduced.** The code path is named. Write out the failing test the fix should start from. The bug-fix playbook reproduces it at implementation.
   - **Neither.** The reporter must supply steps or environment. List what was tried.
7. **Check out of scope.** Read `.out-of-scope/*.md`. Name any match and how it bears on the issue. "None match" is a valid result.
8. **Check duplicates and routing.** Search the tracker for the same signature, or the same area, trigger, and symptom. Record a confident duplicate, or an owner in another repository or team, as a recommendation in the triage notes. Never close, move, relabel, or reassign.
9. **Draft the brief.** Write the agent brief with testable acceptance criteria and scope boundaries. Never present a hypothesis as a finding in the title or brief.
10. **Review the brief.** Run an **interrogate** panel of two models on the brief. Fix untestable criteria and unstated assumptions it finds.
11. **Check blast radius.** Run **blast-radius** on every standard issue that changes the repository, except a reproduced report whose fix is clear. Write what it finds into the brief's scope boundaries.
12. **Run the readiness check** in [`../references/readiness.md`](../references/readiness.md). Step 14 replaces its interactive outcome and grilling. Record the checklist and a Decision log in the triage notes. The log has one entry per decision you settled: what, why, the evidence, and the result.
13. **Assign priority.** Apply the `## Priority rubric` section of the repository's issue-tracker adapter. After a step-2 stop, step 3 has not run, so read the body, comments, and linked reports yourself first. Read the live priority and the latest `Priority:` line in earlier triage notes. That line is authoritative. With no such line, write only when the live value is unset. With a `set by triage` line, write only when the live value is unset or still equals that line's value. A `set by <person>` line always blocks the write. When none of these allows a write, a person chose the value, so keep it and write nothing. When you write a value, add a Decision log entry `Priority: <value>, set by triage, rule: <lane condition and evidence>`. When the adapter has no rubric section, set Urgent only for a live fault affecting users, leave other priorities unset, and ask in the triage notes for a `setup-work-skills` re-run to configure priority.
14. **End the run.** Write the triage notes and the agent brief through the adapter's issue-artifact operation, and write the priority through the adapter. Then end with exactly one outcome:
    - **Every item holds.** Apply the Type, any Theme, and the ready label.
    - **An item fails.** Apply the Type, any Theme, and no ready label. Ask one round of questions, each with a recommended answer. Ask only for a decision that meets all three ADR criteria, a fact only the reporter has, or a scope choice with more than one reasonable answer. Never ask for a fact you could look up. Apply `Needs info` when only the reporter can answer, and leave `Needs triage` otherwise.

Apply only Type, Theme, and Triage labels, plus the priority. Priority is never a readiness item. Recommend `Won't fix` in the notes rather than applying it. Model roles follow patina-mode's Models section: `how` explorers, `why` investigators, and the `interrogate` panel take their own roles, and reproduction takes the bug-fix role. No progress narration reaches the tracker.

**Reply:** the first line is `Triage outcome: <label>` when a ready label was applied, or `Needs input:` followed by the round's questions. Then the Type, Theme, and priority, the reproduction result, and links to the triage notes and agent brief.

**Priority-only mode.** For "backfill priorities" or a request to prioritize without triaging, skip steps 2 through 12 and 14. List the open issues with no priority, leaving out any whose latest `Priority:` line says `set by <person>`. Apply the rubric to each. Present one table with the issue, proposed priority, matched rule, and evidence. Write nothing until a maintainer approves the table. Then, for each approved row, write the priority and add step 13's Decision log entry to the issue's triage notes through the adapter's issue-artifact operation, creating the notes when none exist. This approval is the one reply this playbook waits for.
